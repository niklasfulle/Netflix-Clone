# 1.12.1 QR device pairing checkpoint

## Goal

Implement #65: secure QR-assisted device login. A signed-out target device
receives an independently revocable Auth.js session only after an authenticated
approver completes fresh password and, when enabled, MFA verification.

## Decisions confirmed

- A valid session is created only on the target device that displayed the QR
  code; the approving phone session is never transferred.
- Approval requires a five-minute recent-authentication step-up. The existing
  application had no such boundary, so it must be introduced as part of this
  release.
- Test seams are the pairing creation/status/cancellation endpoints, manual
  code resolution, and authenticated approval/denial endpoints.

## Completed in this checkpoint

- Added QR device-pairing terms to `CONTEXT.md`.
- Added `QrDevicePairingStatus` and `QrDevicePairingRequest` persistence with
  separate hashed manual-code, approval, polling, and future exchange secrets.
- Added `RecentAuthenticationGrant`, bound to one user and one revocable
  Auth.js session, with a five-minute expiry.
- Added migration `20260821130000_add_qr_device_pairing`.
- Added `createQrDevicePairingService` with a five-minute lifetime, canonical
  HTTPS origin enforcement (HTTP only for loopback), an 80-bit grouped manual
  code, and 256-bit approval/poll secrets.
- Added `createRecentAuthenticationService`; it grants a recent-auth proof only
  after a fresh password and, when enabled, an atomically consumed MFA proof.
- Added a fail-closed approval service slice: approval checks the recent-auth
  proof and delegates a single atomic pending-request transition to persistence.
- Added red-green unit and migration contract tests. Current targeted result:
  3 suites, 6 tests passed. Prisma schema formatting and client generation pass.

## Next slice

Create the Prisma adapters and authenticated routes. The approval route must
atomically bind one request to its approver, require the recent-auth grant, and
make a one-time exchange available only to the target device. Do not write the
UI until those contracts are tested.

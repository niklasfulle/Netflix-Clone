# Deployment status trust contract

Netflix Clone publishes one bounded **Deployment Record** for the latest
deployment attempt in each environment. The record is evidence about the
deployment process; it is separate from live health monitoring and never grants
the application access to Docker or SSH.

## Trust boundary

Each LXC owns an Ed25519 signing key generated by Ansible at:

```text
/etc/netflix-clone/deployment-status.key
```

The private key is root-owned with mode `0600` and is never mounted into a
container. The host publisher signs the exact bounded JSON payload and writes an
envelope atomically. The application receives only this directory read-only:

```text
/var/lib/netflix-deployment-status/records/<environment>.json
/var/lib/netflix-deployment-status/trusted-keys/<environment>.pem
```

The application verifies the fixed environment key, signature, schema,
environment identity, field allowlists, file type, and size before returning a
record through the administrator-only API. A browser can request or display a
record but cannot create a valid signature or replace the read-only host mount.

The record contains only:

- environment, application version, deployment identifier, and image identity;
- deployment start, completion, and publication timestamps;
- deployment and migration results;
- bounded application, HTTPS, and monitoring health results;
- bounded rollback result and previous image reference; and
- the safe basename of the verified pre-migration backup.

It never contains environment values, database URLs, SSH or registry
credentials, authentication secrets, unrestricted logs, SQL, or backup data.

## Lifecycle and failure semantics

Ansible publishes `in_progress` before the database backup and refreshes the
record after migrations and each health boundary. It publishes `succeeded` only
after application, canonical HTTPS, and monitoring checks have passed.

The guarded deployment rescue first publishes `failed` with the completed and
incomplete checks, then attempts the existing rollback. A verified rollback
replaces that record with `rolled_back`. If Ansible or the host exits between
steps, the last signed partial or failed record remains visible instead of
being inferred as success.

The admin API and `/admin/system` distinguish:

| Trust state | Meaning |
| --- | --- |
| Verified deployment | Signature and schema are valid and the record is current |
| Signed status is stale | Signature is valid, but a completed record is older than 24 hours or an active record older than 30 minutes |
| Status unavailable | The approved record or public key cannot be read |
| Signature verification failed | Envelope, key identity, signature, payload, or environment binding was rejected; payload details are hidden |

Records more than five minutes in the future are also stale to expose clock
drift. Live service health must still be evaluated through `/api/health` and the
system monitor; a signed historical success is not a live readiness signal.
The overview also reads the bounded local scheduled-backup result. A timeout,
lock conflict, dump failure, or restore-verification failure is presented as a
failure even when the last signed application deployment itself succeeded.

## Peer-environment transport

`DEPLOYMENT_STATUS_APPROVED_PEERS` contains only the explicitly approved
environment names. Ansible configures staging to approve production and
production to approve staging. This allowlist does not create a network or SSH
connection. A peer remains **unavailable** until an operator transports both its
signed record and public key through an already authenticated administrative
channel.

For example, to expose the production summary on staging, copy only these two
public artifacts from production to their matching paths on staging:

```text
records/production.json
trusted-keys/production.pem
```

Never copy `deployment-status.key`. The receiving host must keep the filenames
bound to the source environment and root-owned. Replacing a trusted peer key is
an explicit trust change and should be performed only during a documented key
rotation.

## Retention and recovery

The publisher retains exactly the latest record per environment and replaces it
atomically. It never removes backup dumps, deployment diagnostics, monitoring
snapshots, or audit events. Consequently, deployment-status retention cannot
delete recovery data; detailed historical deployment retention belongs in a
separate append-only operations system.

If a host key is lost, generate a new host key through Ansible, redistribute
only the new public key to approved peers, and perform a deployment to create a
new signed record. Existing records signed with the old key must not be treated
as verified under the replacement key.
